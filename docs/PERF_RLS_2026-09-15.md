## 1. `auth_rls_initplan` — 69 politiques à réécrire, 29 tables

`auth.uid()` est `STABLE`, pas `IMMUTABLE`. Écrit nu dans un `WHERE` de politique,
PostgreSQL le **rappelle pour chaque ligne examinée**. Sur `users` (75 035 fiches), une
lecture, c'est 75 035 appels.

Enveloppé dans `( SELECT auth.uid() )`, il devient un **InitPlan** : évalué une fois au
début de la requête. Même fonction, même session, même résultat.

| mesure | valeur |
|---|---|
| politiques `public` au total | **94** |
| contenant `auth.uid()` / `auth.role()` / `auth.jwt()` | **70** |
| en contenant un **à nu**, donc à réécrire | **69** |
| tables concernées | **29** |
| déjà entièrement enveloppées, laissées telles quelles | **1** |

### Le prédicat n'est pas « contient `auth.uid()` »

C'est **« contient un `auth.uid()` pas encore enveloppé »**. PostgreSQL rend
`( SELECT auth.uid() )` sous la forme `( SELECT auth.uid() AS uid )` : le texte relu n'est
jamais égal au texte écrit. Avec le prédicat naïf, la migration aurait réécrit les mêmes 70
politiques **à chaque passage** — sans effet, mais une migration qui refait son travail à
chaque fois ne peut plus servir de preuve.

### Pourquoi la migration ne recopie aucune politique

Recopier 70 expressions, c'est 70 occasions de se tromper d'un caractère — et une faute de
frappe dans un `WHERE` de politique **ne se voit pas** : elle ouvre ou ferme un accès en
silence. Une transcription fige aussi l'état d'hier : si une politique change d'ici à
l'application, le fichier la **remettrait** dans son état d'hier.

La migration lit donc la définition **courante** et n'y applique qu'une réécriture
mécanique. La sémantique est préservée **par construction**. Chaque `DROP`/`CREATE` exécuté
est imprimé par `RAISE NOTICE` : **c'est ce journal qu'il faut lire après coup.**

### Le détail qui rend le fichier rejouable

On **déballe** d'abord (`( SELECT auth.uid() AS uid )` → `auth.uid()`), puis on **emballe**.
Sans le premier temps, un second passage produirait `( SELECT ( SELECT auth.uid() ) )`.
Deuxième passage attendu : **0 examinée, 0 réécrite.**

## 2. `multiple_permissive_policies` — 21 lignes, 13 résolues, 8 refusées

Quand plusieurs politiques permissives couvrent la même commande pour le même rôle,
PostgreSQL les évalue **toutes** et fait le OU. Quatre politiques de lecture sur `reviews` =
quatre expressions par ligne.

### Pourquoi le OU séparé `USING` / `WITH CHECK` est exact

C'est le point à vérifier **avant** de fusionner quoi que ce soit, et il n'est pas évident.

PostgreSQL **n'apparie pas** le `USING` d'une politique avec le `WITH CHECK` de la même
politique. Pour une commande donnée, il combine d'un côté **tous** les `USING` permissifs
par OU, de l'autre **tous** les `WITH CHECK` permissifs par OU, et les applique
indépendamment.

Fusionner en `USING (a1 OR a2 OR a3)` + `WITH CHECK (b1 OR b2 OR b3)` rend donc
**exactement** ce que la base calculait déjà. Ce n'est pas une approximation.

Précaution : pour un `UPDATE` **sans** `WITH CHECK`, PostgreSQL réutilise le `USING` comme
contrôle de la nouvelle ligne. La fusion fait de même (`coalesce(with_check, qual)`) — sans
ça, elle relâcherait le contrôle. *(Aucun des deux groupes `UPDATE` fusionnés n'est dans ce
cas : tous leurs membres ont un `WITH CHECK`. La précaution est là pour le jour où.)*

de l'application et **refuse** le groupe si elle n'est plus vraie.

### ⚠️ Les 8 lignes REFUSÉES — elles ne sont pas oubliées

| table | action | rôle | membres | pourquoi on ne fusionne pas |
|---|---|---|---|---|
| `appointments` | SELECT | `authenticated` | `Patients see own appointments` *(TO public)*, `appointments_select_doctor` *(TO authenticated)* | **rôles différents** |
| `review_reports` | INSERT | `anon` | `reports_admin_all` **[ALL]**, `reports_authenticated_create` | **un membre est `FOR ALL`** |
| `review_reports` | INSERT | `authenticated` | idem | idem |
| `review_reports` | SELECT | `anon` | `reports_admin_all` **[ALL]**, `reports_user_reads_own` | idem |
| `review_reports` | SELECT | `authenticated` | idem | idem |
| `specialties` | SELECT | `authenticated` | `Admins manage specialties` **[ALL]**, `Anyone can read specialties` | idem |
| `waiting_list` | INSERT | `anon` | `Anyone can join waiting list`, `wl_insert_anon` | **rôles différents** |
| `wilayas` | SELECT | `authenticated` | `Admins manage wilayas` **[ALL]**, `Anyone can read wilayas` | idem |

**`FOR ALL`** : fusionner obligerait à éclater le `ALL` en quatre politiques, donc à
**réécrire** la logique d'accès. Hors mandat.

**Rôles différents** : la fusion imposerait l'**union** des rôles, donc soumettrait `anon` à
une condition qu'il ne voyait pas. En pratique cette condition rendrait `false` pour lui —
mais *« en pratique »* n'est pas *« par construction »*, et la règle de ce lot est de ne
rien élargir. **Un raisonnement qui marche « en pratique » est exactement ce qui produit une
fuite six mois plus tard.**

## 3. Hors périmètre : `storage.objects`

**Dix** politiques de `storage.objects` portent le même `auth.uid()` nu. Elles ne sont pas
dans la migration :

```
storage.objects  →  propriétaire : supabase_storage_admin
la migration s'applique en :        postgres
```

Un `DROP POLICY` peut y être refusé, et **un refus au milieu d'une migration annule tout le
reste**. C'est au stratège de trancher, en connaissance de cause, dans un lot à part.

## 4. Vérification — après application

```sql
-- 1. plus aucun auth.*() à nu
select tablename, policyname from pg_policies
 where schemaname = 'public'
   and regexp_replace(coalesce(qual,'')||' '||coalesce(with_check,''),
         '\(\s*SELECT\s+auth\.(uid|role|jwt)\(\)(\s+AS\s+\w+)?\s*\)', '', 'gi')
       ~ 'auth\.(uid|role|jwt)\(\)';
-- attendu : 0 ligne

-- 2. les groupes restants
select tablename, cmd, count(*) from pg_policies
 where schemaname='public' and permissive='PERMISSIVE'
 group by 1,2 having count(*)>1 order by 1,2;
-- attendu : les 8 lignes refusées ci-dessus, et elles seules
```

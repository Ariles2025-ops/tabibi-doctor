## Défaut trouvé — le médecin ne voit pas le rendez-vous de son patient

**C'est le défaut le plus sérieux du parcours, et il est nouveau dans cette recette.**

Le rendez-vous porte `doctor_id = doctor_profiles.id` (`85a6972c-…`), ce qui est correct : c'est ce que
`get_available_slots` et la garde utilisent. Mais le tableau de bord médecin interroge la table avec
l'identifiant de **compte** :

```
doctor-dashboard.html:555
  '/rest/v1/appointments?select=*&doctor_id=eq.' + encodeURIComponent(userId)
```

où `userId` vient de `supabase.auth.getSession()`, donc `2ed31cea-…`.

Mesure directe sur le rendez-vous créé pendant ce parcours :

| Requête | Lignes |
|---|---|
| `doctor_id = 2ed31cea-…` (identifiant de compte, ce que fait le code) | **0** |
| `doctor_id = 85a6972c-…` (identifiant de fiche, ce qui est stocké) | **1** |

La fonction fautive, `fetchDoctorRdvsFromSupabase`, alimente **trois** vues à la fois via
`refreshDoctorRdvs()` : « Aujourd'hui », l'agenda, et « Mes RDV ». Les trois sont donc aveugles.

C'est ce qui explique le « 0 RDV aujourd'hui / Aucun RDV aujourd'hui » observé sur R1 au parcours 1 :
ce n'était pas un agenda vide, c'était une requête qui ne peut rien trouver.

Ailleurs dans le même fichier, le bon chemin existe pourtant : les lignes 949 et 1103 passent par
`window.tabibiDoctor.getMyDoctorId()`. Le fichier mélange les deux espaces d'identifiants.

**Conséquence produit : un patient réserve, le médecin ne le voit nulle part.** À trancher : bloquant
pour la vague ou correctif immédiat dans une PR à part.

  `v4_hsl1`, et des `bc_*` dans l'illustration du hero. Les six clés vérifiées **existent** dans

  défaut d'ordre corrigé pour la clé publiable. À consigner, pas à corriger ce soir.
